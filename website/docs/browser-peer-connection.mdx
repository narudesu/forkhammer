# JSON-RPC peer integration

Forkhammer supports PeerJS/WebRTC, Supabase Realtime, and a worker-hosted WebSocket transport. All transports use [`json-rpc-2.0`](https://www.npmjs.com/package/json-rpc-2.0) to call worker methods.

## Connection flow

1. The browser creates a PeerJS peer and waits for its ID.
2. The browser writes a `browser_peer_ready` event to Supabase:

   ```json
   { "event_type": "browser_peer_ready", "data": { "peerId": "<browser-peer-id>" } }
   ```

3. The worker sees the event and connects to that peer ID.
4. On `connection`, the browser keeps the data connection open and sends JSON-RPC messages.

PeerJS is only used for signaling. After the connection opens, requests and responses travel directly between the two peers.

## Worker-hosted WebSocket

The worker listens on the port configured by `[worker.peer.websocket].port` (default `8787`). It publishes a `browser_websocket_token_issued` event to the configured feed table containing a cryptographically random, single-use token and port. After a connected client disconnects, the worker publishes a fresh token; use the newest token event in the feed. Configure your network/firewall to expose this port, preferably through a TLS-terminating reverse proxy, and connect the browser to:

```text
wss://your-worker-host/peer?token=<token-from-feed-event>
```

For local development without TLS, use `ws://localhost:8787/peer?token=...`. The token is consumed at successful WebSocket upgrade; a second connection attempt with it is rejected. Previous token events remain in the append-only feed history, but their tokens are no longer accepted. Anyone with feed access can read the token, so treat feed access as credential access and use `wss://` outside local development.

After connecting, send and receive the same JSON-RPC messages documented below. Session updates are JSON-RPC notifications.

To smoke-test the endpoint from the Forkhammer repository, pass the full URL (including a fresh token) to:

```bash
bun run test:peer-websocket -- 'wss://your-worker-host/peer?token=<token-from-feed-event>'
```

The script sends a `get-config` JSON-RPC request and exits successfully when it receives a response. Since the token is single-use, get a new feed token for each test run.

## JSON-RPC messages

The worker exposes these methods:

- `get-config`
- `list-worktrees`
- `list-sessions`
- `list-recent-project-sessions`
- `get-session`
- `create-worktree`
- `create-session`
- `subscribe-session`
- `unsubscribe-session`
- `archive-session`
- `prompt-session`

`list-recent-project-sessions` accepts `{ project }` and returns `{ project, sessions }`. It aggregates all worktrees and orders sessions newest-first; each session's `cwd` identifies its worktree.

A request has an `id`, and its response uses the same ID:

```json
{ "jsonrpc": "2.0", "id": 1, "method": "list-worktrees", "params": { "project": "demo" } }
```

```json
{ "jsonrpc": "2.0", "id": 1, "result": { "project": "demo", "worktrees": [] } }
```

Failures are returned as a JSON-RPC `error` response. Method parameters and result shapes are defined in [`src/peer-protocol/peer-protocol.ts`](https://github.com/narudesu/forkhammer/blob/main/src/peer-protocol/peer-protocol.ts).

## Integrate the browser peer

Install the two client dependencies:

```bash
bun add peerjs json-rpc-2.0
```

A minimal browser-side client looks like this:

```ts
import Peer from "peerjs";
import { JSONRPCClient } from "json-rpc-2.0";

const peer = new Peer();

peer.on("open", async (peerId) => {
  // Insert this event using the application's Supabase client.
  await supabase.from("ultrafeed_item").insert({
    event_type: "browser_peer_ready",
    data: { peerId },
  });
});

peer.on("connection", (connection) => {
  connection.on("open", () => {
    const rpc = new JSONRPCClient((message) => connection.send(message));

    connection.on("data", (message) => {
      // The worker sends session updates as JSON-RPC notifications.
      if (message && typeof message === "object" &&
          (message as { method?: string }).method === "session-event") {
        handleSessionEvent((message as { params: unknown }).params);
        return;
      }
      void rpc.receive(message as never);
    });

    rpc.request("list-worktrees", { project: "demo" })
      .then((result) => console.log(result))
      .catch((error) => console.error(error));
  });

  connection.on("close", () => {
    // Mark the client disconnected and create/announce a new peer when needed.
  });
});
```

Use the same `JSONRPCClient` instance for all requests so it can match responses to request IDs. Keep the PeerJS peer alive, handle `connection`/`close`, and announce a new `browser_peer_ready` event after reconnecting.

## Session updates

After calling `subscribe-session`, the worker sends notifications (they have a `method` but no request ID):

```json
{
  "jsonrpc": "2.0",
  "method": "session-event",
  "params": { "sessionPath": "...", "type": "assistant_message", "text": "..." }
}
```

Handle these notifications separately; do not pass them to the request-response flow.
